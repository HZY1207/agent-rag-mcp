# 10 · 评测与交付

> 本步新增：`eval/qa_set.json`（15 题评测集）、`scripts/evaluate.py`（自动评测）、`eval/report.json`（本次运行报告）。
> 本步完成：项目 README 终稿、全链路验收。

## 一、为什么要做评测

"看起来能用"和"可以交付"之间差一个**可量化**。没有评测：

- 改了提示词/阈值，无法判断是变好还是变坏；
- 不知道检索到底有没有召回正确片段，还是模型在硬猜；
- 无法回答"知识库外的问题会不会胡说"。

所以本步建立一套**小而可复现**的评测：一条命令跑完，输出指标与逐题明细。

## 二、评测集设计（15 题）

| 类型 | 数量 | 考察点 |
|---|---|---|
| `kb` 知识库问答 | 11 | 检索是否召回正确片段 + 回答是否覆盖关键事实 + 是否带引用 |
| `refusal` 知识库外 | 2 | 资料没写的问题，是否明确拒答而不是编造 |
| `calc` 工具计算 | 2 | 是否正确调用计算器并给出准确数字 |

每题两个字段很关键：

- `evidence`：检索指标用——top-3 切片中是否包含这些**证据词**（如 `提前 3 个工作日`）；
- `expected_keywords`：生成指标用——最终回答必须覆盖的事实（如 `3`、`10`、`200`）。

两者分开，才能区分"没检索到"和"检索到了但答漏了"。

知识库为 `samples/星尘科技员工手册.md`（演示用虚拟资料）。

## 三、指标定义

| 指标 | 定义 | 说明 |
|---|---|---|
| Hit@3 | top-3 切片中至少一条含证据词的比例 | 检索召回能力 |
| MRR | 首个相关切片名次的倒数均值 | 排序质量（越接近 1 越好） |
| 关键词覆盖率 | 回答命中的期望关键词 / 期望关键词总数 | 生成完整性 |
| 引用率 | 带 ≥1 条引用的知识库回答占比 | 可溯源 |
| 拒答准确率 | 知识库外问题明确拒答的比例 | 抗幻觉 |
| 计算准确率 | 最终答案包含正确数字的比例 | 工具调用正确性 |
| P50 / P95 延迟 | 端到端耗时分位数（服务端 `done` 事件计时） | 体验 |

**口径说明**：知识库题为端到端调用 `/api/agent/chat`（Agent 自主检索 + 生成），
检索指标另调 `/api/knowledge/search` 直接看 top-3；评测前重启服务以清空语义缓存，
避免缓存命中干扰延迟与检索统计。

### 两个值得说的细节

1. **第 12 题用了 2 次工具**：Agent 先检索了一次不满意，又换关键词检索了一次，
   最后明确回答"手册未提及股票代码"，并指出该手册是演示用虚拟资料。这正是 Agent 相比
   固定 RAG 管道的价值：**自主决定检索策略**。
2. **MRR = 0.9545 而不是 1**：有一题的证据词首次出现在第 2 个切片。Hit@3 仍是 100%，
   说明 top-3 足够兜住；如果将来把 top_k 调成 1，这题就会漏。

## 五、局限与下一步

诚实说明（面试时也是加分项）：

| 局限 | 影响 | 改进方向 |
|---|---|---|
| 评测集小（15 题，单一文档） | 指标方差大、易过拟合 | 扩到 50~100 题、多文档、按主题分层 |
| 关键词匹配偏机械 | 同义表达可能误判漏判 | 引入 LLM-as-judge 或人工标注评分 |
| 单次运行 | 无法区分波动 | 每题跑 3 次取均值/方差 |
| 未覆盖对抗场景 | 不知道抗注入能力 | 加提示注入、越权、超长输入用例 |
| 语义缓存/限流为单机内存 | 多实例不一致 | Redis 替换实现 |

## 六、如何复现

```powershell
# 1. 启动服务（建议先重启，清空语义缓存）
python -m uvicorn app.main:app --port 8000

# 2. 跑评测
.venv\Scripts\python.exe -X utf8 scripts\evaluate.py
# 指标与逐题明细打印到控制台，同时写入 eval/report.json
```
