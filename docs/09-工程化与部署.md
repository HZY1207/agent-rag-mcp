## 一、语义缓存：让"重复问题"不再花钱

### 1. 为什么需要

一次完整问答的成本 = 向量化 + 检索 + LLM 生成（大头）。真实产品里大量问题是重复或近义的
（"年假多少天" / "年假有几天"）。缓存命中时响应从秒级降到亚秒级，同时省掉 token。

### 2. 为什么不用字符串缓存

`question == cached_question` 只能命中一模一样的问法，价值有限。
**语义缓存**把问题编码成向量，比较余弦相似度：换个说法也能命中。

```
问题 ──embedding──▶ 向量 ──余弦相似度──▶ 与缓存中历史问题比较
                                        │
                        ≥ 0.96 ─────────┴──▶ 直接返回缓存答案
                        < 0.96 ─────────────▶ 正常走 RAG + LLM
```

### 3. 阈值为什么是 0.96（重要取舍）

"年假多少天"和"病假多少天"的向量相似度可能高达 0.9，但答案完全不同。
**语义缓存宁可不命中，也不能答错**，所以阈值定得很高（0.96），基本只命中
"换个说法 / 多个标点 / 同义改写"的问法。

### 4. 工程约束

| 约束 | 设计 |
|---|---|
| 只缓存可信场景 | 仅"单轮、无 session_id"的问题；带上下文时同一句话答案可能不同 |
| Mock 模式不缓存 | 避免配好 Key 后返回演示答案 |
| 容量与过期 | TTL（默认 1 小时）+ 上限 500 条（超出淘汰最旧） |
| 线程安全 | `threading.Lock`；向量计算丢线程池（`asyncio.to_thread`） |
| 单实例局限 | 进程内内存，重启即失效；多实例应换 Redis（get/put 接口不变） |

### 5. 实测

```
1) 语义缓存：同一个问题同步问两次
  第一次： 1858 ms   cached=False   引用 2 条
  第二次：  421 ms   cached=True    cache_score=1.0
  加速比：4.4x
  两次回答一致：PASS
  缓存生效：PASS
```

第二次仍要 ~400ms，是问题向量化的开销（fastembed CPU 推理）；检索 + LLM 已全部跳过。

## 二、限流：保护接口

`RateLimitMiddleware`：按 IP 的**滑动窗口**（deque 存时间戳），默认 120 次/分钟。

- 只统计 `/api` 路径；`OPTIONS` 预检和 `/api/health` 不计入；
- 超限返回 `429` + 统一响应体 `code=4290` + `Retry-After` 头；
- 单机内存实现；多实例换 Redis（同样的滑动窗口逻辑）。

实测（快速打 130 次 `GET /api/sessions`）：

```
状态码分布：{200: 118, 429: 12}
429 响应头 Retry-After=16
body={'code': 4290, 'message': '请求过于频繁（120 次/分钟），请 16 秒后重试', 'data': None}
```

> 注意：评测/压测脚本会触发限流，可临时调大 `RATE_LIMIT_PER_MINUTE` 或关闭 `RATE_LIMIT_ENABLED`。

## 三、Docker 部署（零 Docker 也能本地跑）

本地开发不需要 Docker（Qdrant 本地文件模式 + SQLite）。Docker 是**部署形态**：

```bash
# 1. 准备配置（LLM_API_KEY 必须）
Copy-Item .env.example .env
# 2. 一键构建 + 启动（API + Qdrant）
docker compose up -d --build
# 3. 访问
#    http://127.0.0.1:8000/app     聊天界面
#    http://127.0.0.1:8000/docs    API 文档
```

### 关键设计

1. **多阶段构建**：阶段 1（node:20-alpine）构建前端；阶段 2（python:3.12-slim）只带构建产物，
   镜像更小，且运行环境没有 Node。
2. **Qdrant 服务端模式**：容器里用 `QDRANT_URL=http://qdrant:6333`。
   本地文件模式的 Qdrant 有单文件锁，不适合容器/多副本。代码里两种模式自动切换
   （`app/services/knowledge.py` 的 `_get_client`）。
3. **持久化**：`./data` 挂载会话 SQLite 与向量模型缓存；Qdrant 数据用命名卷。
4. **配置注入**：`.env` 通过 `env_file` 注入，Key 不进镜像；`.dockerignore` 排除 `.env`、`.venv`、`node_modules`。
5. **构建加速**（国内网络）：

```bash
docker compose build \
  --build-arg PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple \
  --build-arg NPM_REGISTRY=https://registry.npmmirror.com
```

### 诚实声明

本机没有安装 Docker，**镜像构建与 compose 编排未在本机实际运行验证**。
已验证的是：Dockerfile / compose 引用的所有配置项（`QDRANT_URL`、`FASTEMBED_CACHE_PATH`、
`SESSION_DB`、`MCP_CONFIG_PATH`）在代码中均有实现，且本地文件模式与 `/app` 静态托管跑通。

## 四、新增配置项

| 配置 | 默认值 | 说明 |
|---|---|---|
| `SEMANTIC_CACHE_ENABLED` | `true` | 语义缓存开关 |
| `SEMANTIC_CACHE_THRESHOLD` | `0.96` | 命中阈值（越高越保守） |
| `SEMANTIC_CACHE_TTL` | `3600` | 条目有效期（秒） |
| `RATE_LIMIT_ENABLED` | `true` | 限流开关 |
| `RATE_LIMIT_PER_MINUTE` | `120` | 每 IP 每分钟请求上限 |
| `QDRANT_URL` | 空 | 空=本地文件模式；填写=服务端模式 |
| `FASTEMBED_CACHE_PATH` | 空 | 向量模型缓存目录（Docker 挂卷） |
