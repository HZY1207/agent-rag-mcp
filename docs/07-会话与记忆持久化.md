# 07 · 会话与记忆持久化（SQLite）

> 本步新增：`app/services/sessions.py`、`app/api/routes/sessions.py`、`app/schemas/sessions.py`、`scripts/smoke_sessions.py`。
> 本步改动：`app/api/routes/chat.py`、`app/api/routes/agent.py`（接入 session_id）、`app/schemas/chat.py`（新增 session_id 字段）。

## 一、为什么"记忆"要放到服务端

第 2~4 步的多轮对话靠客户端每次回传 `history` 数组，问题：

| 客户端传 history | 服务端会话（本步） |
|---|---|
| 刷新页面就丢 | 持久化在 SQLite，刷新/换设备都在 |
| 上下文长度由客户端控制 | 服务端统一裁剪（最近 20 条） |
| 无法审计、无法分析 | 消息可查询、可统计、可做评测 |
| 请求体越来越大 | 请求只带 session_id + 本轮消息 |

## 二、存储设计

零额外依赖：Python 标准库 `sqlite3` 足够（单机、数据量小）。表结构：

```sql
sessions(id TEXT PK, title TEXT, created_at TEXT, updated_at TEXT)
messages(id INTEGER PK AUTOINCREMENT, session_id TEXT, role TEXT,
         content TEXT, citations TEXT, created_at TEXT)
```

工程细节：

- **连接单例 + 线程锁**：FastAPI 的同步调用可能落在不同线程，`sqlite3.connect(..., check_same_thread=False)`
  再用一把 `threading.Lock` 把写入串行化；
- **WAL 模式**（`PRAGMA journal_mode=WAL`）：读写并发更好，SQLite 的标准实践；
- **时间统一 ISO 8601 字符串**：可读、可直接按字符串排序；
- **引用存 JSON 文本**：`citations` 列，读取时反序列化。

## 三、接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/sessions` | 创建会话 |
| GET | `/api/sessions` | 会话列表（按更新时间倒序，含消息数） |
| GET | `/api/sessions/{id}` | 会话详情（含全部历史消息） |
| PATCH | `/api/sessions/{id}` | 重命名 |
| DELETE | `/api/sessions/{id}` | 删除（连同消息） |

对话接口的约定：**带上 `session_id` 即进入"服务端会话模式"**——

```json
POST /api/agent/chat
{ "message": "那它需要提前多久申请？", "session_id": "d57621356e92" }
```

服务端自动完成：确保会话存在 → 读历史（最近 20 条）→ 记录本轮问题 →
生成回答 → 写入回答与引用 → 更新会话时间。

会话不存在时**自动创建**（幂等），首条消息自动成为标题（截断 20 字符）。

## 四、为什么不直接用 LangGraph checkpointer

LangGraph 自带 checkpointer 可以持久化"图执行状态"，但那是**执行中间态**（给"中断后恢复运行"用的）。
本项目要的是**用户可见的聊天记录**：前端要列表、要标题、要引用卡片、要能删除。
两者目标不同，自己存消息更简单直接（也方便做过会儿的评测）。
真要做"人工审批后继续执行"时，再引入 checkpointer 不迟。
